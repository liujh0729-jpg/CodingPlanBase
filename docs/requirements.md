# 需求摘要

定位：开源 SaaS 底座。保留「租户 + 账号 + 网关 + 计费 + 支付骨架」，任何具体行业业务都不进本仓。

## 产品

给一个平台方交付给 B 端客户的多租户底座：平台开通租户并拨付额度，租户管理员管自己的人和额度并向平台订购软件能力，租户成员签发 `sk-` 令牌调用大模型；一个账号可以同属几个租户，切到哪个租户就用哪个租户的身份与额度。管理员配一次上游 Key，即可按 token 计费，需要收费时打开外部支付开关。

## 两个身份轴与分工

| 轴 | 记在哪 | 取值 | 判定 |
|---|---|---|---|
| 全局身份 | `users.role` | `1` 普通用户 / `10` 平台管理员 / `100` 超级管理员（`0` 保留，不可授予） | `isAdmin()` ≥10、`isRoot()` ≥100 |
| 租户内权限 | `tenant_members.role` | `1` 成员 / `5` 租户管理员（只有这两档） | `isTenantAdmin()`＝本次会话有当前租户，且在这个租户里是 5 |

```
平台（全局身份 ≥10）─开通/停用/拨额度池/开通管理员/补加成员─▶ 租户 ─建号/拉人/启停/从池划拨─▶ 本租户成员
   ▲                                                  ▲            │
   └──────── 订单、退款、渠道、系统设置 ──────────────┘            │
       租户侧只在「设置 → 订购管理」下单与看单；一个账号可同属几个租户，
       切到哪个租户就用哪个租户的身份与额度（租户内权限 5＝该租户的管理员）
```

| 身份 | 能做什么 |
|---|---|
| 成员（租户内 `1`） | 在本租户里签发自己的 `sk-` 令牌、看价目表与自己在该租户的用量、改密码；额度由该租户管理员从额度池划拨，用完即被网关拒调用 |
| 租户管理员（租户内 `5`） | 顶栏「管理菜单」＝ 用户管理（建号、把已有账号拉进本租户、启停、重置密码、设定成员 / 管理员、从额度池划拨与回收）+ 模型使用记录（本租户成员的调用与额度流水）；前台「设置」比成员多一项订购管理（向平台订购软件能力 + 只读本租户订购记录） |
| 平台管理员（全局 `10`） | 除「系统设置」外的全部后台板块：租户（下钻成员与补加、软件权益、订购记录、池流水）、账号、订单、支付、渠道、全部令牌、价目表、全平台日志；支付管理的开关与商品目录也归它配。前台与租户管理员同款（含「设置 → 订购管理」），但平台直属账号没有当前租户，进去只有全平台订购记录，不下单 |
| 超级管理员（全局 `100`） | 在管理员之上可处置管理员与超管账号、调整全局角色阶梯顶端，并独占「系统设置」：额度换算与零售倍率、目录同步间隔、上游密钥、开放注册。前台菜单与租户管理员逐项一致（含订购管理＝全平台订购记录） |

- 登录、注册、刷新、改密全部由本系统签发 JWT，不依赖外部账号服务；开放注册可后台关闭。注册二选一：创建租户（自己＝该租户的管理员）或输入租户编码加入（普通成员），没有审批环节；两处都没选就是「未加入租户」，能登录、能看价目表，但签发不了令牌（后端 422），界面引导先用顶栏「创建或加入租户」。
- 可授予的全局身份只有 `1 / 10 / 100`；`ROLE_GUEST 0` 是沿用 newapi 的保留常量，不在阶梯里，接口会报「角色不合法」。租户内权限由 `assertMemberRole` 收在 `1 成员 / 5 管理员` 两档，提交别的值 422。「租户管理员」不要求任何全局身份——普通用户可以是某个租户的管理员，平台管理员也可以被补加进某个租户当成员；一个人在各租户里的权限档互相独立。
- 超管账号至少保留一个，禁止自杀式停用；全局角色只能由不低于目标角色的操作者授予。
- 越界动作既不在界面渲染，也在服务端拒绝：租户看不到平台后台菜单，平台管理员与本租户成员进不了租户的管理菜单（文案不同），不属于本租户的成员读写统一报 404「该账号不是本租户的成员」。管理员深链到不属于自己菜单树的路由（如平台管理员进 `/console`、租户进 `/admin/settings`）时，侧栏选中态退回所属区域的首栏，页面本身仍出「无访问权限」。侧栏的分组标题（AI 服务 / 设置 / 平台管理后台 / 管理菜单）只是标签，不可折叠：分组下的菜单项任何角色进来都常驻可见，不需要先点开分组。
- 前后台两套菜单靠命名区分，不靠近义撞名：管理员返回前台后就是调用方视角，侧栏与本租户成员相比只多一项「设置 → 订购管理」（当前租户的管理员与平台管理员 / 超管都一样，因为订购管理对这两种身份渲染），所以后台板块一律取「管理侧」名字——`全部令牌`、`价目表`、`全平台日志`，与前台的 `API 令牌`、`模型与价格`、`用量与额度` 不会认错。
- 平台管理员也进不了「系统设置」：侧栏不列这个板块，深链只出「无访问权限」，`PUT /settings` 里除支付三键（`chandler_enabled` / `chandler_base_url` / `chandler_products`，跟着「支付管理」板块开放）之外的键一律要求超管；`POST /gateway/setup`（写上游密钥）同口径。读取仍对管理员全量开放，因为「全平台日志」要拿 `quota_per_unit` 换算金额。

## 额度口径

- 金额一律以人民币计，界面不出现美元；`1 元 = quota_per_unit（默认 500000）额度`，零售价 = 批发价 × `pricing_markup`（默认 1.10）。
- 换算参数由超管在「系统设置」维护，写入即被计费链路读到，并有服务端边界：`quota_per_unit ≥ 1`（为 0 时额度无法换算金额）、`0.01 ≤ pricing_markup ≤ 100`（填 0 会把整张价目表算成 0 元）、`new_user_quota ≥ 0`、布尔键只收 `true` / `false`；一条越界整单拒绝，不会出现半套配置生效。
- 「目录同步间隔（分钟）」是活控件：定时器每 60 秒醒一次现场读该值（`AIPDD_CATALOG_SYNC_INTERVAL_MINUTES` 环境变量优先），保存后最迟 1 分钟按新间隔执行，改 0 立即停，全程不用重启后端。
- 一条链：平台 → 租户额度池（`tenants.quota_pool` + `tenant_quota_txns`）→ 该租户成员（`tenant_members.quota` + 带 `tenant_id` 的 `quota_txns`）。唯一的例外是平台侧建号 / 补加成员时填的初始额度，那笔直接给到成员、不动额度池；除此之外平台不给租户成员发额度，租户也不能凭空造额度；任何一环都不允许透支。
- 租户在自己这一层发放与回收额度：`POST /console/users/:id/quota` 的 `delta` 正数发放（池余量不足整单拒绝）、负数回收（最多收到该成员在本租户的现有额度）；池流水按**额度池视角**记账（发放为负、回收为正），说明落动作原文，租户管理员在「管理菜单 → 用户管理」的额度池流水里逐笔可见。
- 额度是用不用 AI 的唯一开关，且**按租户各一份**：`tenant_members.quota` 归零后，网关在令牌鉴权之后、选路与计费之前直接拒调用（`429 当前租户内额度不足，请联系该租户管理员分配额度`），不限额令牌同样挡；被拒的调用不写消耗流水。回收额度＝立刻停用，再划拨＝立刻恢复，不需要改状态或重签令牌；同一个人另一个租户里的额度不受影响。
- 「在本租户停用」一个成员只冻结这条成员关系（本租户给的额度不能用、切进来不能调用），账号本身与他在其他租户里的额度、令牌都不动；被停用或被移除的成员，其当前租户自动退到他的下一个可用租户。
- 消耗实时累加到 `tenant_members.used_quota` 与 `tenants.used_quota`，池余量不因消耗回落。

## AI 服务（大模型网关）

- 渠道可按 new-api 的方式自由配置：新建时先选**上游标准模板**（OpenAI 兼容、DeepSeek、火山引擎、通义、智谱、Moonshot、硅基流动、xAI、Mistral、Perplexity、OpenRouter、Gemini、Anthropic、自定义中转），一次带出类型编号 / 默认 Base URL / 上游路径前缀，再按实际改；类型编号沿用 new-api 的 `constant/channel.go`，模板只覆盖 OpenAI / Anthropic 两类兼容载荷的请求体形状，请求体结构不同的源（Azure、Gemini 原生、Cohere、Bedrock 等）不在模板范围内。
- AIPDD 是其中一个受管来源：首次使用由超级管理员在「系统设置 → AIPDD 接入」填 Key 建立受管渠道，并可一键拉取全量模型目录（按 revision 做增量，已手动钉价的模型不被覆盖）。受管渠道不进新建下拉，由向导维护。
- 目录来源地址是 AIPDD 平台的固定量（默认 `https://api.aipdd.work`），接入向导只显示不可改、`POST /gateway/setup` 也只收密钥；确需指向别的地址用后端 `AIPDD_BASE_URL` 环境变量覆盖。
- 渠道选路：先按模型过滤（模型清单留空＝接受该分组下的全部模型），再取最高优先级层，层内按权重随机，全层权重为 0 时等概率；同渠道内多密钥按顺序轮换。
- 故障转移：一次调用最多试 3 个渠道，失败的渠道进排除名单后重新选路（同层剩余渠道 → 次高优先级层）。连接失败、`408`、`429`、`5xx`、密钥被拒会换渠道；其余 `4xx` 是请求本身的问题，直接透传不换渠道。切换发生在往客户端写第一个字节之前，全部失败时透传最后一次上游的状态与报文，连接层失败报 `503`。
- 密钥级失败（`401`/`403` 或报文含 `invalid api key`）先在同一个渠道内换下一个密钥（最多 3 个），换成功就不算渠道失败；全部密钥都被拒才算这个渠道的密钥坏了。自动禁用只由密钥级失败与连通性测试失败触发，`5xx`/限流等暂时故障只换渠道，不打下线整个渠道。
- 渠道配置入库前校验：名称、密钥、Base URL 必填；类型必须是模板里存在的编号（老编号 `0` 直接被 `422` 拒掉并提示从模板选择）；上游路径前缀补前导 `/`、去尾斜杠后入库，留空即 `/v1`；模型重定向、请求头覆盖、参数覆盖必须是 JSON 对象（前两者的值还得是字符串），非法值直接 `422` 拒收，不会静默降级成「没有覆盖」。
- 转发落点只由 `base_url` + `api_prefix` 决定：把请求路径里的 `/v1` 换成该前缀（火山 `/api/v3`、通义 `/compatible-mode/v1`、智谱 `/api/paas/v4`、Gemini `/v1beta/openai`），`base_url` 已含同一前缀时不重复拼；改前缀后立即生效，不需要重启。Anthropic（`14`）打 `{prefix}/messages` 并带 `x-api-key` + `anthropic-version`，其余类型打 `{prefix}/chat/completions`。
- 支持模型可「从上游拉取」：按 `{api_prefix}/models` 请求该渠道，清单去重排序后回填。只对**已保存**的渠道开放，由后端读库里存的地址与密钥发起请求——上游密钥不经浏览器，管理端临时填的地址也不会成为出网目标。
- 上游错误报文里的平台侧渠道密钥一律先掩码再出后端：透传给调用方、写用量日志、写渠道备注都只给掩码版本。
- 对外协议：OpenAI 兼容 `/v1/chat/completions`、Anthropic 兼容 `/v1/messages`，鉴权为 `Authorization: Bearer sk-<令牌>`。
- 计费两种：按 token（输入单价 × 补全倍率 × 缓存读/写倍率 × 模型倍率）与按次固定价（标价本身，不乘倍率）；额度换算比例可配。模型倍率是一个模型一个系数，对所有分组统一生效；「可见分组」只决定模型出现在哪些分组的模型清单里，不参与算价。
- 令牌维度：令牌记在**签发时所在的租户**里（`tokens.tenant_id`），换了租户就用不了别的租户签的令牌；独立额度或跟随「这个租户给这个成员的可用额度」、模型白名单、IP 白名单、有效期、启停；调用先扣令牌余额再扣成员在本租户的额度，余额不足按可用额度封顶。没有当前租户的账号签发不了令牌（422）。
- IP 白名单的写法：`*`、精确 IPv4/IPv6、CIDR 网段（`5.6.7.0/24`）、前缀通配（`10.0.*`），逗号或换行分隔、入库去重归一。来源 IP 取 `X-Forwarded-For` 首段，IPv4 网段按掩码运算判定，命中任意一条即放行，全不命中记 `403`。
- 白名单在**建/改令牌时**就校验：非法规则（如 `5.6.7.0/33`、`abc`、`300.1.1.1`）整条请求 `422` 拒收并点名是哪一条，库里保持原值。写错的规则在线上只会表现为「来源 IP 不在白名单内」，分不清是笔误还是真没授权，所以不接受它落库。
- 有效期只有两个状态：非正数一律收成 `-1`＝永不过期，界面显示「永不过期」。新建留空＝永不过期；编辑时留空＝不修改，填 0 天＝改回永不过期。
- 额度换算（`1 元 = N 额度`）只有后端设置一个来源：令牌表单的换算提示与步进、日志的金额折算都读 `GET /gateway/wallet`（任何登录用户可取），界面不写死比例；比例没读到就只显示额度，不编造金额。
- 租户被平台停用后，该租户成员已签发的令牌立即拒绝调用，报错指名租户；「在本租户停用成员」只影响这个租户里的身份，不牵连他在别的租户。
- 每次调用落一条日志：类型、用户、**所属租户**（`logs.tenant_id`，平台「全平台日志」据此出一列归属租户）、令牌、模型、渠道、输入/输出 tokens、消耗额度、耗时、是否流式、上游错误摘要；令牌与渠道删除后日志保留快照。

## 支付（B 端）

- 场景是 B 端付费：租户向平台订阅软件、买断功能、购买额度包。付款人以自己的平台身份发起预支付，因此账号需先绑定平台账号。
- 订单主体是租户：`payment_orders.tenant_id` 为归属，`user_id` 是下单并付款的租户管理员。平台侧「订单管理」做检索、核对与退款；租户侧只有前台「设置 → 订购管理」（软件订购页签下单，订购记录页签只读：继续支付与结果核对可用，退款不可自助）。同一个「订购管理」菜单对「当前租户的管理员」与平台管理员 / 超管都渲染：平台管理员 / 超管进去只有「订购记录」，读的是全平台单据（多一列归属租户），「软件订购」页签不渲染，服务端也拒绝平台直属账号下单（报「当前账号未归属任何租户」）。
- 履约落点：订阅与功能买断写租户权益（`tenant_entitlements`）并把 `tenants.expires_at` 往后顺延；额度包到账进额度池。
- 退款按已服务天数折算，退款成功即回收该租户的权益 / 冲回额度池。
- 支付能力由后台开关控制：关闭时订购入口显示「未开通」，额度改由平台划拨——「租户管理 → 划拨额度」打进额度池，「账号管理 → 分配额度」点名在哪个租户里给某个成员（账号必须先在该租户里，否则 404「该账号不在这个租户里，没有可处置的租户内额度」），租户管理员再在「管理菜单 → 用户管理」从池里分配给自家成员。

## 边界

- 演示库为仓库内 SQLite；MySQL / PostgreSQL 由派生的方言 schema 与建表 DDL 交付，业务代码不写方言 SQL。
- 不含行业业务、不做多上游厂商适配、不做营销/内容/工单等模块。要加请先确认是否属于底座。
